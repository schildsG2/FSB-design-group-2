Local Environment Setup

Getting UE running on your own machine — the clone-to-dev-server sequence, what tends to break along the way and why, and the tools worth knowing about before you fight the terminal alone.

The setup sequence

Five steps, run once in order: clone the repo, install two separate dependency sets (Ruby and JS), set up the database, then start the dev server.

1. Clone
Pull the repo down locally for the first time.
→
2. bundle install
Installs the Ruby/Rails dependencies the app needs to run.
→
3. yarn install
Installs the JS/frontend dependencies — a separate package tree from step 2.
→
4. db:setup
Creates and seeds the local database. Needs Docker running first.
→
5. yarn run dev
Starts the dev server. Site lives at g2.test.
# from the g2-setup skill
git clone git@github.com:g2crowd/ue.git && cd ue
bundle install
yarn install
bin/rails db:setup      # needs Docker running
yarn run dev

Once yarn run dev is running, the site lives at https://www.g2.test — not localhost.

It's a sequence, not a command

yarn run dev looks like one command, but it's actually kicking off a chain — and a break anywhere in that chain can look like a totally unrelated failure on screen.

1
Colima starts
The lightweight VM that runs Docker on your Mac. Nothing containerized can start until this is up.
2
Docker containers come up
Postgres and any other service containers the app depends on.
3
DB ports bind
The app connects to Postgres over the expected local port.
4
puma-dev starts
Routes g2.test requests to the app server running Puma.
5
Four watchers start in parallel
Background processes that recompile Sass, rebuild JS, and rebuild the Elevate design-system bundle as you edit — each one is a separate thing that can silently die.

When it breaks

Because it's a chain, the symptom you see rarely names the actual cause. These four cover most of what goes wrong day to day.

Symptom Cause Fix
Styles broken Sass watcher died yarn run sass:watch &
500s everywhere Postgres down / migration pending bin/rails db:migrate
curl returns 000 1 puma thread, monopolized Kill workers, restart puma-dev
Broken after branch switch Stale Elevate build yarn run elevate:build

Terms worth knowing

Words you'll see in error messages and setup docs before they mean anything.

Runs a piece of infrastructure (like Postgres) in an isolated environment, identical on every machine. You don't install Postgres yourself — you run its container.
In design terms: like a component in a design system — pre-built, self-contained, the same everywhere it's used.
Docker itself is built for Linux, so on a Mac, Colima runs a small Linux VM in the background to host it. If Colima isn't running, no container can start — it's the very first link in the chain.
Puma is the Ruby app server that runs the Rails app. puma-dev is a thin layer on top that routes a friendly local domain (g2.test) to whichever Puma instance is running — it's why the site loads at a real-looking URL instead of localhost:3000.
A background process that watches a folder for file changes and rebuilds output automatically — Sass into CSS, or the Elevate design-system bundle. It runs the whole time you're developing, and because it runs silently, a dead watcher is easy to mistake for a code bug.
In design terms: like Figma auto-saving as you work — except here, if it silently stops, nothing tells you.
Every change to the database structure (a new column, a new table) is written as a migration file and applied in order. If your local database is missing one — usually after pulling a teammate's branch — you'll see errors until you run bin/rails db:migrate.
bundle install installs Ruby gems (the backend); yarn install installs JS packages (the frontend). They're tracked and installed completely independently — pulling a branch that adds a new gem won't do anything to your JS packages, and vice versa. If something's missing after pulling, it's worth running both.
