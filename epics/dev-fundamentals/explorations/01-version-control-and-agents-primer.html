Version Control & Agents Primer

A grounding in git fundamentals, what actually happens in a pull request, and how to point an agent at a repo — written for early-level builders working in design/dev crossover projects like this one.

The core loop

Version control (git) is just a way of tracking changes to files over time, in small labeled snapshots you can always return to. Everything else — branches, PRs, agents — is built on top of this loop.

1. Working directory
The files on your machine right now. Edit freely — nothing is tracked until you say so.
→
2. Staged
git add marks specific changes as "ready to be part of the next snapshot."
→
3. Commit
git commit saves a permanent, labeled snapshot of the staged changes.
→
4. Push
git push sends your commits to the shared remote (GitHub) so others can see them.

A branch is just a separate line of this loop — a parallel copy of history that lets you make commits without touching main until you're ready. That's what makes it safe to experiment.

Terms worth knowing

You don't need to memorize these — but recognizing them will make PR descriptions, agent output, and teammates' Slack messages far less mysterious.

git clone <url> downloads the full history of a repo and sets it up locally, with a link back to the remote (called origin).
Lets you make commits without affecting main. Convention: one branch per feature or fix, named something like sc/dev-fundamentals-primer.
git switch -c my-branch creates and moves you onto a new branch. Your working directory changes to reflect that branch's state.
A line-by-line comparison between two states of the code. Lines added show as +green, removed as -red. This is what a PR review is actually reading.
Merge combines two branches and keeps both histories intact (creates a merge commit). Rebase replays your commits on top of the latest main, producing a cleaner, linear history. Most PRs are merged via a "squash merge" — all your commits collapse into one.
Your local repo is a full copy — origin is just the conventional name for where it came from / syncs back to. git pull brings origin's changes to you; git push sends yours there.
A pointer to whatever commit your working directory currently reflects. Almost always "the tip of the branch you're on" — but this is also what agents mean when they say "at HEAD."
A request to merge your branch into main, opened on GitHub — bundles your commits, a diff, a description, and a place for teammates (or agents) to comment. Covered in detail below.

Anatomy of a pull request

A PR is the unit of review and the unit of shipping. Here's the lifecycle, start to finish.

1
Branch off main
Give it a descriptive name — often prefixed with your initials or a ticket number.
2
Commit as you go
Small, logical commits with clear messages are worth more than one giant commit at the end — they make review and rollback much easier.
3
Push and open the PR
Write a description: what changed, why, and how to verify it. Link the ticket. This is the first thing a reviewer (human or agent) reads.
4
CI checks run automatically
Tests, linters, type checks. A red check means something needs fixing before anyone should review the logic.
5
Review & comments
Reviewers comment inline on the diff. You push new commits in response — the PR updates in place, it doesn't restart.
6
Approve & merge
Once approved and checks are green, the branch merges into main (usually squashed into one clean commit) and the branch is deleted.

Using an agent to look at a repo

An agent with file access can read a codebase the same way you'd skim it — just faster, and it can hold more of it in mind at once. A few prompts that actually work well: 

  • "Explore this repo and give me a high-level summary of what it does"
  • "Where is the login button styled? I want to change its color"
  • "Summarize what changed in the last 5 commits"
  • "Look at PR #142 and tell me what the reviewer is asking for"
  • "Find every place this component is used before I rename it"

The more specific the question, the better the answer — "fix my code" gives an agent nothing to anchor on, while "the submit button doesn't disable while the form is saving" gives it a concrete thing to find.

The hidden files that support agents & skills

A repo isn't just the visible code — dotfiles and config quietly shape how tools and agents behave in it. This repository is itself a working example:

File / folder What it does
.git/ The actual database of every commit, branch, and history — this is what makes it a repo at all. Never edit by hand.
.gitignore Lists files/folders git should never track (build artifacts, local secrets, node_modules, etc).
CLAUDE.md Auto-loaded project context for an agent — in this repo, it's the file describing the Elevate design system, folder structure, and conventions you're reading right now, in effect.
.claude/*.skill Packaged, repeatable workflows an agent can run on command — this repo has new-epic, new-exploration, and setup-squad-explorations, which is exactly how this exploration's folder and gallery card got scaffolded.

The pattern generalizes: any codebase you get pulled into may have its own CLAUDE.md or equivalent — checking for one before asking an agent to make changes is usually the fastest way to get output that matches the team's actual conventions instead of generic defaults.
