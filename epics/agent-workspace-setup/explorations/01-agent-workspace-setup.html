Agent Workspace Setup

The files an agent reads before you type anything — personal preferences, a repo's own instructions, and how they stack — for early-level builders on design/dev crossover projects like this one.

The core idea

Most of what shapes an agent's behavior isn't typed into the chat — it's loaded in from files, layered from broad to specific. Each layer can narrow what the one above it says, but none of them can override what a repo's own committed instructions say.

A repo's own instructions always win. Your personal layer should narrow the gap between "what this repo says" and "how I like to work" — never contradict it outright. When they genuinely disagree, that's a sign the personal layer needs updating, not the other way around.

Where each layer lives

Two kinds of files, each with a personal and a project version. Knowing which is which tells you where to actually make a change.

File / folder What it does
~/CLAUDE.md (personal) Lives on your own machine, outside any repo. Preferences you want every agent, in every project, to already know — not reviewed by anyone but you.
CLAUDE.md / AGENTS.md (project) Committed to the repo itself. Project conventions and policy, visible to and binding on anyone who clones it — arrives through the same review process as code.
skills (personal) Packaged workflows kept alongside your personal config. Yours alone — nothing in any repo depends on them existing.
.claude/skills/ (project) Packaged inside the repo itself — this repo's own new-epic and new-exploration skills, or the g2-server skill from Local Environment Setup. Available to anyone working in that repo.

The personal/project split isn't about which file is "more important" — it's about who it's reviewed by. A repo's own instructions go through the same PR process as its code; your personal layer usually goes through no one. That asymmetry is exactly why personal preferences move into a shared repo file deliberately, never automatically.

When it goes wrong

The most common failure isn't a missing file — it's a layer writing into the wrong one.

A cautionary case

An agent working across both layers once wrote personal preference content directly into a repo's shared instruction file — as if one person's private checklist were team policy. It looked harmless, just more text in a file already full of text, but it meant a personal working style now read as binding on everyone who cloned the repo.

The fix: pull the personal content back out into its own layer, and keep the repo's instruction file policy-only — scoped to what's actually true for everyone, not what one person prefers. If something learned on the job really is durable and repo-specific, it belongs in that repo's own instructions, proposed through the normal review process — not injected directly by an agent mid-session.

Worth knowing about

Two things that make the layering above mostly automatic once they're set up.

Packaged skills

Teach it once, reuse it forever

A skill applies the same personal/project split to a whole workflow, not just a preference. The g2-server skill from Local Environment Setup is one example: the setup sequence and its failure modes, written once and handed to an agent by name instead of re-explained every session.

Checking before you ask

Five seconds that save a generic answer

Before asking an agent to change something in an unfamiliar repo, check whether it already has its own instruction file — covered in Version Control & Agents Primer's "Hidden files" section. If one exists, your agent is already reading it; if not, /init is the fastest way to create a starting point.

Terms worth knowing

You don't need to memorize these — but recognizing them will make an unfamiliar repo's setup far less mysterious on day one.

Loaded into context before you type a single prompt. A personal copy lives on your own machine; a project copy lives committed inside the repo — both get read, but only the project copy is visible to anyone else who clones it.
In design terms: like a component library's usage notes — read before anyone touches the file, so edits match what's already there.
A set of steps written once and invoked by name, instead of re-explained in every session. Can live in your personal config or committed inside a repo — see Where each layer lives, above.
In design terms: like a saved plugin command — write the steps once, run it by name forever after.
A leading dot (.claude/, .gitignore) hides a file from a normal directory listing. Hidden from view, not from the agent — it reads these before anything else.
In design terms: like a layer marked "do not export" — present, doing real work, just hidden from the default view.
Personal scope (your machine) vs. project scope (committed to the repo). Same file type, different authority — personal scope is a suggestion to yourself; project scope is policy for the team.
In design terms: like your own plugin settings vs. a shared library's style guide — one is yours alone, the other is the team's.
Org policy, then a repo's own committed instructions, then your personal layer. Project scope always wins over personal scope — covered in The core idea, above.
In design terms: like brand guidelines overriding a personal style preference — the shared standard wins when they conflict.
