Version Control & Agents Primer

Git fundamentals, PR mechanics, and working with an agent on a repo — for early-level builders on design/dev crossover projects like this one.

The core loop

Version control just tracks changes to files as small, labeled snapshots you can always return to. You branch off main to work safely, and the loop isn't done until your change is reviewed, approved, and merged back.

1. Work locally
Branch off main, then edit and commit as you go. Nothing here is visible to anyone but you.
→
2. Share it
Push your branch and open a PR — a request for your changes to be merged into main.
→
3. Get it reviewed
A teammate (or agent) reads the diff, comments, and signs off once it looks right.
→
4. Merged into main
Your change joins main for good — the loop closes, and everyone builds on top of it next.

Main only changes at the two tinted ends — branched off at the start, merged into at the end. Everything between happens safely on your own branch. Shipping a change, below, walks through that stretch step by step.

Using an agent to look at a repo

You know what should happen — you direct, the agent executes. It can read a codebase the way you'd skim it, just faster, and hold more of it in mind at once. A few prompts that work well: 

  • "Explore this repo and give me a high-level summary of what it does"
  • "Where is the login button styled? I want to change its color"
  • "Summarize what changed in the last 5 commits"
  • "Look at PR #142 and tell me what the reviewer is asking for"
  • "Find every place this component is used before I rename it"

/init is worth knowing on its own: it's a built-in skill that scans a repo and writes a starter CLAUDE.md for it. Landing in a codebase that doesn't have one yet (see Hidden files below) is exactly when to reach for it.

Specificity is what makes any of this work — "fix my code" gives an agent nothing to anchor on; "the submit button doesn't disable while saving" gives it something to find.

Shipping a change

The full walkthrough, branch to merge — including the commands behind each step and this org's own conventions for branch names and PR titles.

1
Branch off main
git switch -c creates a parallel line of history — a safe place to experiment without touching main. Give it a descriptive name.
2
Commit as you go
git add stages a change, git commit saves it as a permanent, labeled snapshot. Small, logical commits are worth more than one giant one at the end — they make review and rollback much easier.
3
Push and open the PR
git push sends your commits to GitHub, then you open a PR: a request for your branch to be merged into main. Write a description — what changed, why, and how to verify it — this is the first thing a reviewer (human or agent) reads.
4
CI checks run automatically
Tests, linters, type checks. A red check means something needs fixing before anyone should review the logic.
5
Review & comments
Reviewers comment inline on the diff. You push new commits in response — the PR updates in place, it doesn't restart.
6
Approve & merge
Once approved and checks are green, the branch merges into main (usually squashed into one clean commit) and the branch is deleted.

G2 Engineering conventions

Branch naming (step 1): <github-username>/<feature-name-or-jira-id> — e.g. schilds/DGTL-84. Merges go to main via rebase merging (no merge commits, clean linear history), and the branch is deleted automatically once merged.

PR title format (step 3): follows conventional commits — <type>: <description> [<jira-ticket>]. A valid Jira ticket is required somewhere in the title or description, or the title should say [NO JIRA]. A bot blocks the PR with a comment if the title doesn't conform. Example: feat: Add relative padding to clipboard [DGTL-84].

Source: G2 Engineering Confluence, "Branching Strategy" — worth a read in full if you're touching a real G2 repo for the first time.

Staying close to a PR with an agent

An engineer reviews the code — that doesn't change. But once your PR is open, you can ask an agent to keep watch on it for you: whether checks are passing, whether a comment is waiting on a reply, and whether the merge actually deployed.

While it's open

Keep tabs without pinging anyone

  • "Is CI green on PR #142 yet? If not, what failed?"
  • "Summarize the reviewer comments on my PR in plain language"
  • "Is there a comment on my PR still waiting on a reply from me?"

Once it's approved

Confirm it actually shipped

  • "Did PR #142 merge cleanly into main?"
  • "Did the deploy pipeline succeed? Where can I see it?"
  • "Was the branch cleaned up after merging?"

The hidden files that support agents & skills

A repo isn't just the visible code — dotfiles and config quietly shape how tools and agents behave in it. This repository is itself a working example:

File / folder What it does
.git/ The actual database of every commit, branch, and history — this is what makes it a repo at all. Never edit by hand.
.gitignore Lists files/folders git should never track (build artifacts, local secrets, node_modules, etc).
CLAUDE.md Auto-loaded project context for an agent — in this repo, it's the file describing the Elevate design system, folder structure, and conventions you're reading right now, in effect.
.claude/*.skill Packaged, repeatable workflows an agent can run on command — this repo has new-epic, new-exploration, and setup-squad-explorations, which is exactly how this exploration's folder and gallery card got scaffolded.

The pattern generalizes: any codebase you get pulled into may have its own CLAUDE.md or equivalent — checking for one before asking an agent to make changes is usually the fastest way to get output that matches the team's actual conventions instead of generic defaults.

Terms worth knowing

You don't need to memorize these — but recognizing them will make PR descriptions, agent output, and teammates' Slack messages far less mysterious.

git clone <url> downloads the full history of a repo and sets it up locally, with a link back to the remote (called origin).
In design terms: like duplicating a shared Figma file into your own drafts — except every past version comes with it.
Lets you make commits without affecting main. One branch per feature or fix — this org names them schilds/DGTL-84-style, covered in Shipping a change above.
In design terms: like a parallel artboard or page — you can rearrange and experiment without touching the shipped version.
git switch -c my-branch creates and moves you onto a new branch. Your working directory changes to reflect that branch's state.
In design terms: like switching between pages in a Figma file — the canvas changes to show that page's content.
A line-by-line comparison between two states of the code. Lines added show as +green, removed as -red. This is what a PR review is actually reading.
In design terms: like redlines on a spec — exactly what moved, what got added, what got deleted.
Merge combines two branches and keeps both histories intact (creates a merge commit). Rebase replays your commits on top of the latest main, producing a cleaner, linear history. Most PRs are merged via a "squash merge" — all your commits collapse into one.
In design terms: like flattening a layered comp into one final export — the intermediate steps collapse, only the result ships.
Your local repo is a full copy — origin is just the conventional name for where it came from / syncs back to. git pull brings origin's changes to you; git push sends yours there.
In design terms: like the shared team library vs. your local copy of it — you publish changes up, and pull others' updates down.
git push uploads the commits you've made locally to origin, updating your branch there to match your branch here. Nothing you commit is visible to anyone else until you push it — this is the step that turns private, local work into something shareable (see Shipping a change, above).
In design terms: like syncing a local file to the shared drive — your edits only exist for others once the upload finishes.
A pointer to whatever commit your working directory currently reflects. Almost always "the tip of the branch you're on" — but this is also what agents mean when they say "at HEAD."
In design terms: like "you are here" on the canvas — which version you're currently looking at and editing.
A request to merge your branch into main, opened on GitHub — bundles your commits, a diff, a description, and a place for teammates (or agents) to comment. Covered in detail above.
In design terms: like sharing a Figma file for a design crit — here's what changed, here's why, please comment before it ships.
