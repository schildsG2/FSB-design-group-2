Workflow steps

Two patterns are running in parallel across the AEO/SEO squads. Neither is mandated — pick based on ticket size and how much of the team needs to be involved.

Pattern A

Analyst/Dev agent spec workflow

Bigger initiatives, new surface area

1
Team kickoff
Before splitting off, meet as a full team (Design, PM, Eng, SEO) to align on the problem, hypothesis, and target metric. ~1–2 days for a new epic, shorter for a well-scoped initiative.
2
Draft the spec together
If a PRD/design spec already exists, start there. If not, use the /analyst agent as a team — feed it the problem, hypothesis, and metric; answer its clarifying questions together rather than solo.
3
Review & correct the spec
Do this as a group before anyone builds anything — check for wrong assumptions, missing technical constraints, and open decisions.
4
Turn the spec into Jira
With Atlassian MCP connected, have the agent create the epic and tickets directly from the agreed spec.
5
Review the generated tickets
Check for sequencing, dependencies, and where design input is actually required.
6
Split the work
Pair up (one technical + one non-technical person per epic) or route individual tickets — decide as a team which are small enough for AgentFarm vs. which need a person driving Claude Code/local setup.
7
Build, with pauses for human review
Don't let an agent run an entire epic unattended.
Pattern B

AgentFarm autopilot

Small, well-defined tickets

1
Ticket created & labeled
In Jira, either by a person or by the Scrum Master Agent from a Slack thread — see Toolkit.
2
AgentFarm pulls it in
Jira Autopilot picks up the labeled ticket automatically.
3
PM agent fills the gaps
Breakdown, acceptance criteria — then hands off to an Engineer agent.
4
Engineer agent implements
Opens a PR, sets up a preview environment, checks CI, and addresses failing checks/feedback.
5
Human review & QA
A human (design or eng) reviews the PR and QAs the preview before merge.

Rule of thumb from the retros: front-load discovery in the planning week for small initiatives instead of letting it bleed into the sprint. Ship true MVPs and iterate in production — full-stack builders pick up the small fixes/iterations afterward rather than waiting for a "finished" first version.

Toolkit

The agents and connections the two patterns above actually run on.

Tool What it's for Notes
Full Stack Companion
AgentFarm, Slack-tagged		 Your bx-monorepo code assistant. Answers "why does this behave this way" questions grounded in actual code, runs AEO markdown QA against any Capterra/SA/GetApp URL and posts results to a Jira comment, and ships small fixes as a PR (shows the diff before opening it). Tag it directly in Slack — no context switch needed.
Scrum Master Agent
AgentFarm		 Turns a Slack message or thread into a well-formed Jira ticket (infers title, description, acceptance criteria); periodically scans the board for hygiene issues; gives release-impact analysis. Also the mechanism behind last retro's "flag stuck tickets" commitment.
Claude Code + Figma MCP Designer-driven component creation — hand off an exact Figma component node, get back a production-ready component (variants, states, Storybook stories, tests, design tokens) generated directly in the codebase. The core of how design work is actually getting "full-stacked" — start here if you're new.
SEO QA Structured-Data Agent Automated QA for AEO/SEO issues — flags AEO-markdown problems and SSR/CSR parity issues. ~67% QA time saved on Capterra tickets so far. Scope is expanding to include UX QA, with the UX team owning fixes.
Atlassian MCP Lets your coding agent read Confluence context and create Jira epics/tickets directly, instead of manual copy-paste. Set this up before your first analyst-agent session — without it, agents can't see Confluence at all.
/analyst agent Drafts a PRD/spec from a problem + hypothesis, asking clarifying questions. Shared from the team's agent repo — ask in-channel for the current link.

Getting set up

Five things to confirm before your first agent-assisted session.

1
Choose your coding environment
Claude Code or OpenCode. Agents are separate per tool, so install/configure in whichever you use.
2
Install the shared agents
Install the shared team agents from the group's shared repo.
3
Connect Atlassian MCP
So your agent can read Confluence and write to Jira.
4
Confirm your repo
Make sure you're working in the correct repo (e.g. cd ~dev/ue) before starting a session.
5
Start in Plan Mode
In Claude Code, run claude, then Shift+Tab to select Plan Mode before planning any work.

Known blockers & guardrails

Pulled from squad retros and the cross-squad FSB learnings doc — read this before you hit the same wall.

One team saw merged PRs/month drop ~60% while PRs reviewed went up ~88% after FSB started — AI-authored PRs take more review rounds and more context to evaluate. Budget for this; don't expect agent-assisted speed to show up as faster shipping until review capacity catches up.
E.g. always use existing Elevate components, keep PRs under ~15 files touched, don't reinvent existing functionality (give examples), follow Baymard best practices.
Watch for AgentFarm splitting one ticket into several redundant sub-issues — catch this at splitting time (adversarial check or manual review) rather than after duplicate work has happened.
Without it, you're stuck manually pasting PRD context. Set this up first.
Save generated .md specs to the relevant Confluence page, not just a local/hidden agent folder — the team needs a shared, durable home for artifacts.
Or contended. Preview-label automation on PRs helps but isn't consistent yet; local setup works but is the slowest path and still throws environment errors for some people.
Claude (Design) produces stronger output but burns tokens fast; Figma Make has struggled to stay within the Elevate design system.
Most of the current investment is getting non-technical people shipping code — less has gone into getting technical people up to speed on product/design thinking, which risks PM (and design) becoming the bottleneck as everyone builds faster. Worth deliberately building this the other direction too (e.g. non-PM/non-designer team members drafting the first spec pass).

AEO-native design principles

Separate from tooling — this is what actually changes in the design thinking, not just the workflow. From the Alternatives Pages — SEO and AEO Design Spec (worked example):

  • If a bot can't see it in the raw HTML, it doesn't exist for AEO. No client-side-only reveals (filters, tabs, accordions) for anything that should be citable — must be server-rendered into the DOM.
  • Every module should come from a database field or arithmetic on one — not a writer, not a model. Labels like "Best for X" should be rule-generated (walk an ordered list of rules, stop at the first that fires, consume the label so nothing repeats) rather than hand-written, so they scale and stay defensible.
  • Print the sample size. "Best for healthcare" isn't citable; "4.6/5 from 34 healthcare reviewers" is.
  • Data density over page length — a well-structured table beats a long page with zero tables.
  • Provenance matters — a visible "data last updated / N verified reviews" line gives both buyers and AI engines a reason to trust the page.

This is a useful pattern to point new designers to when they ask "what's actually different about designing for AEO vs. designing normally?"
